# 02-too-many-tools

## Question

How does a Claude model's tool-selection accuracy change as the number of available tools grows, and does giving it a way to search for tools (instead of seeing all of them at once) help?

This measures only the model's **first decision** for each request: which tool it calls (if any) and with what arguments. No tool is actually executed, and there is no multi-turn loop — one API call per case (two for the router).

## Design

6 variants, same dataset, same base system prompt:

| Variant | What it does |
|---|---|
| `todas_15` | 15 tools visible at once (the smallest nested set) |
| `todas_30` | 30 tools visible at once |
| `todas_60` | all 60 tools visible at once |
| `buscador_60` | all 60 tools, all deferred (`defer_loading: true`) behind the server-side tool search tool (`tool_search_tool_regex_20251119`) — the model must search before it can call anything |
| `buscador_60_noconf` | same as `buscador_60` (same 60 tools, same search mechanism), with one extra sentence in the system prompt telling the model not to ask for confirmation when it already has what it needs — added to isolate whether `buscador_60`'s failures come from over-confirming or from not finding the right tool |
| `router_60` | two calls: first classify the request into one of 6 areas (structured output, no tools), then call with only the 10 tools of that area |

All variants use `tool_choice: auto` (the model decides whether to call anything) and the same base system prompt, which tells it to call a tool only when the request is clear and to treat the user's text as data, not instructions. The exact prompt used for `buscador_60_noconf` is also saved to `results/prompt_buscador_60_noconf.txt` for reproducibility.

## Data

- `herramientas.json` — 60 tool definitions (`name`, `description`, `input_schema`), 10 per area across 6 areas (`citas`, `cuenta`, `pagos`, `notificaciones`, `documentos`, `soporte`). Each entry also carries `objetivo` (whether some test case actually expects this tool — 12 do) and `desde` (15/30/60: the smallest variant that includes it; the three sizes are nested).
- `casos.jsonl` — 250 test cases (`texto`, `herramienta_esperada`, `args_esperados`), with `tipo` in `claro` / `rebuscado` / `ambiguo` / `fuera_de_ambito` / `malicioso`.

## How to reproduce

```bash
pip install anthropic python-dotenv
```

Create a `.env` file with:

```
ANTHROPIC_API_KEY=sk-ant-...
```

Small test run:

```bash
python3 ejecutar.py --limit 10
```

Full dataset, specific variants only:

```bash
python3 ejecutar.py --variantes todas_15 todas_60 buscador_60
```

Re-view a previous run's report without spending anything:

```bash
python3 informe.py results/results_XXXX.jsonl
```

Estimate input tokens before running anything for real:

```bash
python3 estimar.py
```

Compare `buscador_60` against `buscador_60_noconf` (reads result files, doesn't call the API):

```bash
python3 comparar_buscador.py results/results_buscador_60_XXXX.jsonl results/results_buscador_60_noconf_XXXX.jsonl
```

## Limitations

- Synthetic dataset: 120 cases carried over from experiment `01-reliable-json`, the other 130 generated by a different model.
- Some case texts reuse wording straight from a tool's `description`, which can make matching easier than it would be with organic user phrasing.
- Only the first decision is scored — no tool is executed, so this doesn't capture how a model recovers (or doesn't) after a wrong first call.
